## 0.2 — 使い続けられるようにする

0.1 で「保存はされるのに画面から使えない」状態だったものを使えるようにした。
不具合の調査を人手に頼らずに済ませる仕組みも入れた。

- 過去の会話の一覧・再開・削除（F-10-2, F-10-3）
- モデルのドラッグ＆ドロップ（F-01-2）
- カメラの構図プリセット、位置の記憶と復元、背景色（F-03）
- ログのファイル出力と日次ローテーション（ADR-0011）
- ソフトウェア描画の検出と警告（R-3）
- 履歴に使うトークン数の設定（未決事項 U-4）
- 起動のスモークテスト

### スモークテストについて

当初は WebdriverIO による UI 自動操作を予定していたが、**アプリを起動して
期待するログが出るかを確かめる方式**に変えた。

0.1 の開発で出た不具合（真っ白なモデル、返事が来ない、半目）はどれも
「起動はするが何かが繋がっていない」類だった。それを捕まえるには、
画面の操作まで自動化しなくても「起動して IPC が疎通する」ことを確かめれば
足りる。WebdriverIO は導入も維持も重く不安定になりやすいので、得られる
確実さに見合わないと判断した。

画面の操作を伴う検証が必要になった時点で改めて検討する。

### 積み残し

- 推論モデル向けの既定設定（未決事項 U-11）。プロバイダ種別ごとに既定値を
  変える余地があるが、適切な値の判断材料が足りない

## 0.3 — PMX に実験的に対応する（完了）

要件の P1。`ModelAdapter` の背後にもう 1 実装を足した（ADR-0004）。

**範囲を「表示までのおまけ」に限る。**

- PMX の読み込みと表示
- テクスチャの解決（相対パスを自前で絶対パスへ直す）
- 揺れ物（ランタイムの stateful-spring）
- モーフ割り当ての UI。モデルごとに手で当てる前提
- MMD モデルの利用規約に関する注意表示（要件 4.4）

### 対象外とするもの

立ち姿と視線の自動調整は追わない。

PMX にはモーフ名にもボーン名にも標準が無い。実装してみたところ、テクスチャの
解決、表情の推測、姿勢の調整、視線、揺れ物と、**ほぼ全項目でモデル固有の
手当てが必要になった**。three.js が MMD を切り離した理由（「MMD 特有の性格が
強い」）とも一致する。

このアプリの中心的な価値は「LLM の返答に応じて表情が変わる」ことであり、
それは正規化された感情語彙がモデルの表情へ素直に対応することを前提にして
いる。VRM は仕様でそれを保証するが、PMX は保証しない。**利用者が事前に
モーフを手で割り当てないと感情表現がまったく動かない。**

そこで PMX は実験的対応と位置づけ、投資はここで止める。詳細は ADR-0015。

## 0.4 — 声を出す（完了）

要件の P2 と F-12。感情セットは既に音声側と共通の語彙として設計してあった（`emotion-protocol.md` 第 5 章）ため、割り当ては素直に収まった。

- VOICEVOX 連携
- [shirataki](https://github.com/t1nyb0x/shirataki) 経由での CeVIO AI 連携
- 正規化感情から各 TTS の感情値・抑揚への割り当て UI
- WebAudio の振幅解析による音声駆動リップシンク。`LipSyncController` の駆動源を差し替えた

実装して分かったこと。

- shirataki は `exportType` を省くと音声ではなくサーバー側のパスが JSON で返る。
  必ず `1` を送る。感情は連想配列ではなく `{name, value}` の配列で受け取る
- 感情成分の名前はキャストごとに違う。「花隈千冬」は 嬉しい / 普通 / 怒り /
  哀しみ / 落ち着き の五つで、驚きに相当する成分は無い。当たらない感情は
  声色を変えず抑揚と速さで差を出す方針にした
- 音量をそのまま口の開き具合にすると、静かな声でほとんど動かない。直近の
  最大音量で正規化する必要がある

## 0.5 — 接続先を切り替える（完了）

Issue #8。同じ人格のままローカル LLM と外部 API を試し比べられるようにした。それまでは人格が同じで接続先違いのキャラクターを 2 つ作るしかなかった。

- 会話を保ったままの接続先切り替え。`CharacterProfile.providerId` の書き換えとして行う
- 使用モデルの記録と表示。切り替えても過去の返答は当時のモデルのまま残る
- 接続先 URL の候補と、README への待ち受け先の一覧

`emotionMode` の置き場所は接続先ごとのまま動かさなかった。`off` は好みの設定ではなく、規約に従えないモデルのための逃げ道であり（要件 R-2、ADR-0003）、キャラクター側へ移すとタグを扱えない接続先で R-2 が再発するため。黙って表情が止まらないよう、その状態であることを画面に出すに留めた。

## 0.6 — 机の上に置く（完了）

要件の P3、F-13。Issue #12、#13、#14。

- 透過・枠なし・常時最前面のマスコット表示。表示倍率は画面の高さに対する背丈の割合
- 窓をモデルの外接箱まで詰め、描かれていない透明な部分はクリックスルー
- ドラッグでウィンドウごと動かす。掴んで動かす対象はカメラではなくモデル
- タスクトレイ常駐
- 吹き出しでの会話。同じウィンドウの中に置く

透過はウィンドウ生成時にしか決められず、`set_transparent` は存在しない。窓は常に透過で作り、通常表示では `body` を不透明に塗ってふさぐ。別ウィンドウにしないのは、Tauri のウィンドウが WebView ごと分かれてストアが割れるため（ADR-0016）。

`set_ignore_cursor_events` を有効にすると WebView へマウスが届かなくなり、画面側では復帰を検知できない。当たり判定は Rust 側でカーソル位置を読んで行う。

**操作できない窓を作らない守りを要件に組み込んだ**（F-13-1、F-13-3、F-13-9、F-13-10）。モデルが描かれていなければ全面が透明になり、全面がクリックスルーとなって、見えず触れない窓が残るため。

## 1.0 の条件

次を満たしたときに 1.0 とする。

1. VRM と PMX の双方が実用に耐える
2. 音声とリップシンクが噛み合っている
3. デスクトップマスコットとして常駐できる
4. 要件定義の機能要件（F-01〜F-11）に未実装が無い
5. 起動から会話までの E2E テストが自動で回っている

## その先

要件の P4。1.0 のあとに検討する。

- 長期記憶と RAG
- function calling によるツール利用
- 複数キャラクターの同時表示と掛け合い

- macOS / Linux 対応

## 版番号の付け方

0.x のあいだは、機能の追加で 2 桁目、修正で 3 桁目を上げる。互換性を壊す変更も 0.x のうちは 2 桁目に含める。保存形式を変える場合は `schemaVersion` を上げ、読み込み時に移行する。
