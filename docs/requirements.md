- 版: 0.1（初版）
- 作成日: 2026-08-29
- 状態: ドラフト（実装着手前）

## 1. 背景・目的とスコープ

### 1.1 目的

VRM および PMX 形式の 3D キャラクターモデルを読み込んで表示し、そのキャラクターと対話できる Windows デスクトップアプリケーションを構築する。対話は LLM が担い、返答内容に応じてモデルが表情・動作で感情を表現する。

単なるチャットクライアントではなく、「画面の向こうに相手がいる」という体験を成立させることを目的とする。したがって本アプリの価値の中心は、テキスト生成そのものではなく、**生成されたテキストをキャラクターの挙動へ変換する層**にある。

### 1.2 MVP のスコープ

MVP（P0）に含むもの:

- VRM モデルの読み込みと表示
- モデルを表示しない、あるいはモデルを設定しない運用
- 手続き的なアイドル挙動（生命感の付与）
- ストリーミング対応のチャット UI
- ローカル LLM および外部 LLM API への接続
- 返答からの感情抽出と表情への反映
- 音声を用いない疑似リップシンク
- キャラクタープロファイルの保存と切り替え
- API キーの安全な保管

MVP に含まないもの:

- PMX 対応（P1）
- モーションクリップ再生、ジェスチャ（P1）
- 音声合成および音声駆動リップシンク（P2）
- 透過マスコットウィンドウ（P3）
- 長期記憶、function calling、複数キャラクター同時表示（P4）
- Windows 以外の OS 向け配布（P4）

### 1.3 想定利用者

自分専用のキャラクター対話環境を構築したい個人。ローカル LLM を自分で用意できる、あるいは外部 API のキーを自分で管理できる程度の技術的素養を持つ。モデルファイルはユーザーが自分で用意する。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| VRM | glTF 2.0 を基盤とした 3D アバターの標準ファイル形式。人型ボーン構造、表情、視線、揺れ物の仕様が標準化されている。0.x 系と 1.0 系が存在する |
| PMX | MikuMikuDance（MMD）で用いられるモデル形式。ボーン・モーフ・物理演算の情報を持つが、モーフ名や構成に標準がなく、モデル制作者ごとに命名が異なる |
| モーフ / ブレンドシェイプ | メッシュ頂点を変形させて表情や口形を作る仕組み。0.0〜1.0 の重みで適用する |
| ビセーム | 発話時の口形。本アプリでは VRM の母音表現 `aa` / `ih` / `ou` / `ee` / `oh` を指す |
| Expression（VRM 1.0） | VRM 1.0 における表情単位。`happy` / `angry` / `sad` / `relaxed` / `surprised` / `neutral` などのプリセット名を持つ |
| BlendShapeProxy（VRM 0.x） | VRM 0.x における表情機構。`JOY` / `ANGRY` / `SORROW` / `FUN` などの名称を用いる |
| SpringBone | 髪やスカートなどを揺らす二次的な物理挙動。VRM 仕様に含まれる |
| VRMA | VRM Animation 形式。VRM 向けのモーションデータ |
| VMD | MMD のモーションデータ形式 |
| キャラクタープロファイル | モデルファイルのパス、システムプロンプト、感情マッピング、音声設定をひとまとめにした本アプリ固有の設定単位 |
| 正規化感情セット | 本アプリが内部で用いる感情の共通語彙。詳細は `emotion-protocol.md` を参照 |

## 3. 機能要件

### F-01 モデルの読み込み

- F-01-1 ファイルピッカーからローカルの VRM ファイル（`.vrm`）を選択して読み込めること
- F-01-2 ウィンドウへのドラッグ＆ドロップで読み込めること
- F-01-3 VRM 0.x および VRM 1.0 の双方を読み込めること
- F-01-4 読み込み対象はローカルファイルシステム上のファイルに限る。URL からの取得は行わない
- F-01-5 読み込みの進捗を表示し、失敗時は理由を提示すること（形式不正、サイズ超過、メモリ不足など）
- F-01-6 直近に読み込んだモデルのパスを記憶し、次回起動時に自動で復元できること
- F-01-7 PMX 形式（`.pmx`）は**実験的対応**とする。表示・テクスチャ・揺れ物までを目安とし、表情はモデルごとの手動割り当てを前提とする。立ち姿と視線の自動調整は対象外。理由は [ADR-0015](adr/0015-pmx-via-third-party-loader.md)

### F-02 モデル非表示・未設定モード

ユーザーの明示要件。

- F-02-1 モデルを設定していない状態でもアプリが起動し、チャット機能が完全に利用できること
- F-02-2 モデルを読み込んだ状態でも 3D ビューを非表示に切り替えられること
- F-02-3 3D ビュー非表示時はレンダリングループを停止し、GPU および CPU を消費しないこと
- F-02-4 非表示状態でも会話の感情推定は継続し、再表示時に現在の感情状態が反映されていること

### F-03 3D ビュー操作

- F-03-1 マウス操作によるカメラの回転、ズーム、平行移動
- F-03-2 カメラ位置のリセット
- F-03-3 顔・上半身・全身のプリセット構図切り替え
- F-03-4 背景色の変更（単色）
- F-03-5 カメラ位置をキャラクタープロファイルへ**自動で保存**し、次に表示するとき復元すること。覚えたものを捨てて既定の構図へ戻せること。マスコット表示は全身に固定するため保存しない（F-13-2）

### F-04 アイドル挙動

無操作・無発話時にもキャラクターが生きて見えること。

- F-04-1 自動まばたき（2〜6 秒のランダム間隔、閉眼 100〜150ms）
- F-04-2 サッケード（微小かつ不規則な視線のゆらぎ）
- F-04-3 LookAt によるカメラまたはマウスカーソルの追従
- F-04-4 呼吸表現（胸部・脊椎ボーンへの約 0.25Hz の周期的変位）
- F-04-5 SpringBone による髪・衣装の揺れ
- F-04-6 各挙動は個別に有効・無効を切り替えられること

### F-05 チャット

- F-05-1 テキスト入力と送信
- F-05-2 応答のストリーミング表示（トークン到着ごとの逐次描画）
- F-05-3 生成中の中断
- F-05-4 直前の応答の再生成
- F-05-5 会話履歴の表示とスクロール
- F-05-6 エラー時の表示（接続失敗、認証失敗、レート制限、コンテキスト超過）
- F-05-7 感情タグは本文表示から除去され、ユーザーには見えないこと

### F-06 LLM プロバイダ設定

- F-06-1 複数のプロバイダプロファイルを保持し、切り替えられること
- F-06-2 対応する接続方式は以下の 4 系統（アダプタとしては 3 種）
  - OpenAI 互換（Ollama / LM Studio / llama.cpp server / OpenAI 公式）
  - Anthropic Messages API
  - Google Gemini API
- F-06-3 プロファイルごとに base URL、モデル名、API キー、生成パラメータ（temperature、max tokens など）を設定できること
- F-06-4 接続テスト機能を持つこと
- F-06-5 可能なプロバイダではモデル一覧を取得して選択肢として提示すること（Ollama の `/api/tags`、OpenAI 互換の `/v1/models` など）
- F-06-6 ローカルプロバイダでは API キーを不要とすること

### F-07 感情タグ解析と表情反映

- F-07-1 LLM の応答ストリームから感情タグを逐次抽出すること
- F-07-2 抽出した感情を正規化感情セットへ解決すること
- F-07-3 タグの強度指定を解釈すること
- F-07-4 感情の切り替えは補間により連続的に行うこと（急激な切り替えを行わない）
- F-07-5 未知タグ、タグ欠如、破損タグのいずれの場合も、本文表示を壊さず `neutral` へ退避すること
- F-07-6 感情推定を無効化する設定を持ち、無効時は常に `neutral` で動作すること
- F-07-7 **感情の切り替えは発話の再生位置に同期させること。** 受信時点で切り替えると、表情が口の動きより先に進み、長い応答では「表情が変わらない」ように見える（ADR-0014）
- F-07-8 推論モデルの思考を本文と混同しないこと。思考は会話に残さず、表情にもリップシンクにも渡さない。ただし進行中であることは表示すること（ADR-0013）
- F-07-9 本文が 1 文字も生成されずに終わった場合、その理由を表示すること
- F-07-10 詳細仕様は `emotion-protocol.md` に従うこと

### F-08 疑似リップシンク

- F-08-1 応答テキストのストリーム受信に同期して口形モーフを駆動すること
- F-08-2 日本語のカナから母音ビセームへ写像すること
- F-08-3 句読点および文末で閉口すること
- F-08-4 音声合成を用いないこと（MVP。0.4 で F-12 により差し替え可能となった）
- F-08-5 将来の音声駆動へ差し替えられるよう、駆動源をインターフェースで分離すること

### F-09 キャラクタープロファイル

- F-09-1 モデルファイルのパス、システムプロンプト（人格定義）、感情マッピング、カメラ構図、音声設定を 1 単位として保存できること
- F-09-2 複数のプロファイルを作成し、切り替えられること
- F-09-3 プロファイルのエクスポートおよびインポート（JSON）。ただしモデルファイル自体は含めず、パス参照とする

### F-10 会話履歴の永続化とコンテキスト管理

- F-10-1 会話をキャラクタープロファイル単位で永続化すること
- F-10-2 新規会話の開始、過去会話の一覧表示と再開、削除ができること
- F-10-3 コンテキスト長を超えないよう、直近 N ターンのスライディングウィンドウで送信履歴を構成すること
- F-10-4 システムプロンプトは常に送信対象に含めること
- F-10-5 要約による長期圧縮は P4 とする

### F-11 API キーの安全な保管

- F-11-1 API キーは Windows 資格情報マネージャーへ保存すること
- F-11-2 設定ファイルには参照キーのみを保存し、平文の API キーを書き出さないこと
- F-11-3 API キーを WebView 側（レンダラプロセス）へ渡さないこと
- F-11-4 ログおよびエラー表示に API キーを含めないこと

### F-12 音声での読み上げ（0.4 で実装）

- F-12-1 返答を音声で読み上げられること。VOICEVOX と CeVIO AI に対応すること。CeVIO へは COM で直に繋ぐ経路と、shirataki を経由して別の機械の CeVIO へ繋ぐ経路の双方を持つこと（ADR-0018）
- F-12-2 合成器・待ち受け先・話者をキャラクタープロファイル単位で設定できること
- F-12-3 正規化感情から各合成器の感情成分・抑揚への割り当てを保持できること。成分の顔ぶれは話者ごとに異なるため、候補名から既定値を推測し、画面から調整できること。**感情タグの強さに応じて中立の声から寄せること。寄せ幅の全体を抑える設定を持つこと**
- F-12-4 返答は文が閉じた時点、および感情が変わる位置で区切って合成すること。返答の完成を待たないこと
- F-12-5 合成した音声は投入順に再生すること。中断時は未再生のものを破棄すること
- F-12-6 合成に失敗しても会話を停止しないこと。ただし失敗の理由は利用者に提示すること
- F-12-7 音声を用いる場合、リップシンクは再生位置と音量で駆動すること（F-08-5 の差し替え）
- F-12-8 音声を用いない設定では従来の疑似リップシンクで動作すること

### F-13 デスクトップマスコット表示（0.6 で実装）

- F-13-1 通常表示とマスコット表示を切り替えられること。マスコット表示は透過・枠なし・常時最前面とする。**マスコット表示はモデルが表示されているときにのみ選べること**
- F-13-2 マスコット表示ではモデルを全身の構図で表示すること（F-03-3 の `full` に固定する）
- F-13-3 表示倍率を設定できること。倍率は画面の高さに対するモデルの背丈の割合として扱い、構図ではなくウィンドウごと拡縮すること。**倍率には下限を設け、掴めない大きさにできないこと**
- F-13-4 ウィンドウはモデルの外接矩形まで縮めること。透明なだけの領域を残さないこと
- F-13-5 モデルが描かれていない透明部分では、背後のウィンドウを操作できること（クリックスルー）
- F-13-6 マスコット表示ではカメラ操作を無効とし、ドラッグはウィンドウの移動に割り当てること。掴んで動かす対象はカメラではなくモデルである
- F-13-7 タスクトレイに常駐し、表示の切り替えと終了ができること
- F-13-8 マスコット表示中も会話ができること。チャットは吹き出しとして同一ウィンドウ内に出すこと
- F-13-9 マスコット表示か否かと表示倍率を保存し、次回の起動時に復元すること。**ただし復元時にモデルを表示できない場合は通常表示で起動すること**
- F-13-10 マスコット表示中にモデルを外した場合、3D ビューを非表示にした場合、またはモデルの読み込みに失敗した場合は、自動的に通常表示へ戻すこと

**操作できないウィンドウを作ってはならない。** マスコット表示は「描かれている
ところだけを拾い、残りはクリックスルーにする」作りである（F-13-5）。モデルが
表示されていなければ全面が透明となり、**全面がクリックスルーになる。** 枠が
なく（F-13-1）、常時最前面で、見えず、触れないウィンドウが残る。プロセスを
終了させる以外に手がない。

F-13-9 で状態を保存するため、この状態は再起動しても続く。モデルの読み込みに
失敗した場合、起動した瞬間から操作できないアプリになる。

モデル未設定と 3D ビュー非表示は例外ではなく正規の状態である（F-02-1、
F-02-2）。したがって逃げ道を用意するのではなく、**その状態に入れないように
する。** F-13-1 で入口を塞ぎ、F-13-10 で表示中の離脱を拾い、F-13-9 で復元を
守る。F-13-3 の下限も同じ理由による。倍率を小さくしすぎて掴めなくなるのも、
同じ詰み方である。

タスクトレイ（F-13-7）も逃げ道にはなるが、これに頼ってはならない。トレイの
実装より先にマスコット表示が動く状態がありうるためである。

**透過は生成時にしか決められない。** Tauri 2.11 に `set_transparent` は存在せず、透過はウィンドウ生成時のフラグである。したがってウィンドウは常に透過で生成し、通常表示では `body` を不透明に塗ってふさぐ（詳細は ADR-0016）。

**別ウィンドウにはしない。** Tauri のウィンドウは WebView ごと分かれるため、状態を持つストア（ADR-0008）が割れる。表情・リップシンク・会話の同期に IPC が必要となり、代償が大きい。F-13-8 で吹き出しを同一ウィンドウ内と定めるのはこのためである。

### F-14 感情と待機のモーション（0.7 で実装）

- F-14-1 待機中もモデルがわずかに動き続けること。重心の移動、体の揺れ、ときおりの小首の傾げなど
- F-14-2 感情に応じて姿勢が変わること。感情タグの強さ（3.2）に応じて度合いを変えること
- F-14-3 モーションはボーンの回転として与え、モーションクリップ（VRMA / VMD）を必要としないこと
- F-14-4 呼吸（F-04-4）や表情と重ねても破綻しないこと。回転の合計には上限を設けること
- F-14-5 モーションは個別に有効・無効を切り替えられること（F-04-6 と同じ扱い）
- F-14-6 VRM を対象とする。PMX ではボーン名が標準化されていないため、当たらなければ何もしないこと（ADR-0004、ADR-0015）

**クリップを読まないのは、モーションのデータを同梱できないからである。** モデルと同じく、配布や改変に制限を課すものが多い（要件 4.4）。利用者に用意させ、感情ごとに割り当てさせるのでは、PMX のモーフ割り当てと同じ負担を強いることになる。手続きで作れば、モデルさえあれば何も用意せずに動く。

表現の幅は狭い。大振りな動きは作れず、重心の移動・小さな傾き・頷き程度に留まる。ただし机の上に置くものであり（F-13）、大きく動くとかえって邪魔になる。クリップ対応は必要になった時点で別に検討する。

腕は肩と上腕までとし、**基準の姿勢から外へ開く方向にのみ動かす**。基準は腕を下ろした状態であり、そこが閉じ切った端になる。閉じる方向へ動かすと**手が胴や腰へ入る**。前腕と手は動かさない。関節を順に回すだけでは円弧を描く機械的な動きになり、胴へも入りやすい。

**VRM の当たり判定は揺れ物のためのものである。** 体に置いた球が、髪やスカートの鎖を潜り込ませないようにする仕組みであり、メッシュ同士の判定は無い。したがって手は胴で止まらない。逆に、腕へも当たり判定が置かれているモデルなら、腕を動かせば髪やスカートが押しのけられて付いてくる。手続きの動きでも揺れ物が反応するぶん、見た目は助けられる。

### F-15 身振り（0.8 で実装）

- F-15-1 返答に身振りを指示できること。`[wave]`、`[nod]`、`[tilt]` のようなインラインタグを用いる（`emotion-protocol.md` 第 3 章の拡張）
- F-15-2 感情タグと併用できること。姿勢（F-14）の上に身振りを重ねること
- F-15-3 身振りは一定時間で終わり、元の姿勢へ戻ること。持続する姿勢ではない
- F-15-4 モデルが対応できない身振りは、何も起こさずに読み飛ばすこと。本文へ漏らさないこと
- F-15-5 VRM を対象とする（F-14-6 と同じ）

**F-14 で身振りを見送ったのは、手をある場所へ運ぶ動きだからである。** 手を振る・指す・胸に当てるといった動作は、腕の長さに依らず手先を目標へ届かせる必要があり、関節を順に回すだけでは作れない。逆運動学を入れるか、モーションクリップを読むかの判断が要る。ここは着手時に決める。

**タグを増やすとパーサへ手を入れる必要がある。** 現在のパーサは正規化感情の名前だけを受け付け、それ以外は本文として表示する（3.6 の劣化規則）。`[wave]` をそのまま出すと**利用者の目に見えてしまう**。身振りのタグを解釈するか、少なくとも既知の身振り名は落とすようにしなければならない。

## 4. 非機能要件

### 4.1 動作環境

| 項目 | 要件 |
|---|---|
| OS | Windows 10 バージョン 1809 以降 / Windows 11、x64 |
| 必須ランタイム | Microsoft Edge WebView2 Runtime |
| GPU | WebGL 2.0 が動作する GPU およびドライバ |
| 配布形態 | インストーラ（MSI または NSIS）。WebView2 のブートストラッパを同梱する |

Windows 11 には WebView2 Runtime が標準搭載されるが、古い Windows 10 には存在しないため、インストーラ側で導入を担保する。

### 4.2 性能

| 項目 | 目標 |
|---|---|
| 描画 | モデル 1 体表示時に 60fps（GPU 性能に依存する） |
| 起動 | ウィンドウ表示まで 3 秒以内 |
| モデル読み込み | 標準的な VRM（20〜60MB）で 5 秒以内 |
| 初回トークン到達 | ローカル LLM の推論速度に依存するため目標値を設けない。ただし送信から接続確立までのアプリ側オーバーヘッドは 100ms 以内 |
| 3D ビュー非表示時 | 描画に起因する CPU / GPU 使用をゼロにすること |

### 4.3 セキュリティ

- テレメトリおよび外部への利用状況送信を行わない
- 外部通信はユーザーが設定した LLM プロバイダ、および将来の TTS エンドポイントに限る
- API キーは Windows 資格情報マネージャーで管理する（F-11）
- Tauri v2 の capabilities により、ファイルシステムへのアクセスをユーザーが明示的に選択したファイルへ限定する
- **例外**: PMX はテクスチャを外部ファイルとして相対参照するため、モデルのあるディレクトリまで許可を広げる。上位へは広げない。VRM は 1 ファイルで完結するのでファイル単位のまま。この差は PMX の形式に由来する不可避なもので、実験的対応に留める理由の一つでもある
- 厳格な CSP を適用し、リモートスクリプトの読み込みおよび実行を禁止する
- モデルファイルは信頼できない入力として扱い、読み込み失敗でアプリが異常終了しないこと

### 4.4 ライセンスと権利

- **いかなるモデルファイルも同梱・再配布しない。** ユーザーが自身で用意したファイルを読み込むのみとする
- MMD 向けモデルは再配布・改変・利用目的に制限を課す規約を持つものが多い。PMX 対応（P1）の際、モデル読み込み画面に利用規約の確認を促す注意文を表示する
- VRM についても同様に、モデルごとのライセンス情報（VRM メタデータに含まれる）を UI から確認できるようにする

### 4.5 国際化

- 日本語を第一言語とする
- UI 文字列はリソースとして外部化し、後から英語を追加できる構造とする
- 疑似リップシンクは日本語カナを前提とする。他言語対応は将来課題とする

### 4.6 保守性

- ロジック層とレンダリング層を分離し、ロジック層の単体テストを可能とする（第 6.6 節）
- モデル形式、LLM プロバイダ、音声合成の 3 点を拡張ポイントとしてインターフェース化する

## 7. 外部インターフェース仕様

### 7.1 OpenAI 互換エンドポイント

Ollama、LM Studio、llama.cpp server、OpenAI 公式をこの 1 アダプタで吸収する。差異は base URL と API キーの有無に集約される。

| 対象 | 既定 base URL | API キー |
|---|---|---|
| Ollama | `http://localhost:11434` | 不要 |
| LM Studio | `http://localhost:1234` | 不要 |
| llama.cpp server | ユーザー指定 | 不要 |
| OpenAI 公式 | `https://api.openai.com` | 必要 |

- エンドポイント: `POST {base_url}/v1/chat/completions`
- リクエスト: `{ model, messages: [{role, content}], stream: true, ... }`
- システムプロンプト: `messages` の先頭に `role: "system"` として含める
- ストリーム: SSE。各行 `data: {...}`、差分は `choices[0].delta.content`、終端は `data: [DONE]`
- モデル一覧: `GET {base_url}/v1/models`（Ollama は `GET /api/tags` も利用可）

### 7.2 Anthropic Messages API

- エンドポイント: `POST https://api.anthropic.com/v1/messages`
- ヘッダ: `x-api-key`、`anthropic-version`、`content-type: application/json`
- **システムプロンプトは `messages` に含めず、トップレベルの `system` フィールドへ置く。** ここが OpenAI 互換との最大の構造差である
- ロール: `user` / `assistant` のみ
- ストリーム: SSE。イベント種別ごとに構造が異なる。本文差分は `content_block_delta` イベントの `delta.text`
- `max_tokens` は必須パラメータ
- Rust 向けの公式 SDK は提供されていないため、`reqwest` による raw HTTP で実装する
- 既定モデル: `claude-opus-5`。その他の選択肢として `claude-sonnet-5`、`claude-haiku-4-5`

### 7.3 Google Gemini API

- エンドポイント: `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:streamGenerateContent?alt=sse`
- 認証: API キー（ヘッダまたはクエリパラメータ）
- リクエスト: `{ contents: [{ role, parts: [{ text }] }], systemInstruction: { parts: [{ text }] } }`
- **ロール名は `user` / `model`。** `assistant` ではない
- システムプロンプトは `systemInstruction` として別項目に置く
- ストリーム: SSE。本文は `candidates[0].content.parts[0].text`

### 7.4 アダプタ層で吸収すべき差異

| 観点 | OpenAI 互換 | Anthropic | Gemini |
|---|---|---|---|
| システムプロンプト | messages 内 `system` ロール | トップレベル `system` | `systemInstruction` |
| アシスタントのロール名 | `assistant` | `assistant` | `model` |
| 認証ヘッダ | `Authorization: Bearer` | `x-api-key` | API キー |
| ストリーム差分の位置 | `choices[0].delta.content` | `content_block_delta.delta.text` | `candidates[0].content.parts[0].text` |
| 終端の表現 | `data: [DONE]` | `message_stop` イベント | ストリーム終了 |
| `max_tokens` | 任意 | 必須 | `generationConfig.maxOutputTokens` |
| トークン使用量 | `usage.prompt_tokens` 他 | `usage.input_tokens` 他 | `usageMetadata` |
| エラー形状 | `error.message` | `error.type` / `error.message` | `error.status` / `error.message` |

内部の共通表現として、プロバイダ非依存の `ChatRequest` / `Delta` / `ProviderError` を定義し、上記差異はすべてアダプタ内部に閉じ込める。

### 7.5 音声合成エンドポイント（P2 で実装、設計は現時点で確定させる）

いずれもローカルの HTTP サーバーへ POST し、WAV を得るという同一形状である。

**VOICEVOX**（既定 `http://localhost:50021`）

- `POST /audio_query?text=&speaker=` でクエリを生成
- `POST /synthesis?speaker=` に上記クエリを渡して WAV を取得
- `GET /speakers` で話者一覧

**shirataki**（既定 `http://localhost:3000`、CeVIO AI を駆動する自作サーバー）

- `POST /v1/voice/create` — text、voiceControl（音量・速度・音高・抑揚・声質）、**emotions（感情値）** を受け取り WAV を返す
- `GET /v1/voice/casts` — キャスト一覧
- `GET /v1/voice/emotions?cast=` — キャスト別の感情一覧
- `POST /v1/voice/sample` — サンプル音声生成
- voiceControl および emotions は省略可能（既定値 50）
- 前提として CeVIO AI 本体と Node サーバーの常駐が必要

**設計上の重要点。** shirataki が感情値を受け取れるため、正規化感情セットは「表情モーフの駆動」と「音声感情の駆動」の**共通通貨**として機能する。MVP で音声を実装しなくとも、感情モデルと `SpeakStyle` の境界を今の段階で確定させておくことで、P2 での統合コストが大きく下がる。対応表は `emotion-protocol.md` に記載する。

```
ProviderProfile {
  id:            string

  kind:          "openai-compatible" | "anthropic" | "gemini"
  baseUrl:       string
  model:         string
  apiKeyRef:     string | null   // 資格情報マネージャー上の参照。実キーは保持しない

    temperature:  number
    maxTokens:    number
    topP:         number | null
  }
```

### 8.3 Conversation

```
Conversation {
  id:          string
  characterId: string
  title:       string
  messages: [
    {
      role:       "user" | "assistant"
      content:    string        // 感情タグを除去済みの本文
      rawContent: string | null // タグを含む原文（再解析用、assistant のみ）
      emotions:   [{ offset: number, emotion: string, intensity: number }] | null
      createdAt:  string
    }
  ]
  createdAt:   string
  updatedAt:   string
}
```

`rawContent` と `emotions` を保持することで、会話再開時に過去の表情推移を再現できる。

### 8.4 EmotionMapping

```
EmotionMapping {
  format:  "vrm" | "pmx"
  modelId: string | null    // PMX ではモデル単位で異なるため識別子を持つ
  entries: {
    [canonicalEmotion: string]: [
      { morphName: string, weight: number }
    ]
  }
}
```

VRM では既定の恒等マッピングで足りるため通常は `null`。PMX ではモデルごとに必須となる。

### 8.5 永続化先

| データ | 保存先 |
|---|---|
| 設定、プロファイル | アプリ設定ディレクトリの JSON（tauri-plugin-store） |
| 会話履歴 | MVP は会話ごとの JSON。件数増大時に SQLite へ移行 |
| API キー | Windows 資格情報マネージャー（keyring） |

## 9. テスト戦略

CLAUDE.md の方針に従い、テストを先に書く。カバレッジ目標はロジック層に対して 80% 以上とする。

### 9.1 Rust 層

- 各 LLM アダプタの SSE パースを、記録済みフィクスチャに対する単体テストで検証する。ネットワークアクセスを伴わないこと
- 特に検証すべきケース: 分割された SSE フレーム、空 delta、`[DONE]` 以外での切断、エラーレスポンス、不正 JSON
- HTTP レベルの結合テストは `wiremock` によるモックサーバーで行う
- 資格情報の保存・取得はインターフェース化し、テスト時はインメモリ実装に差し替える

### 9.2 TypeScript 層（Vitest）

重点対象:

- **感情タグのインクリメンタルパーサ。** チャンク境界をまたぐケースを網羅する（`[` のみ、`[hap`、`[happy` で切れる、`[happy:0` で切れる、タグ内に改行、閉じない `[`、連続タグ、本文中の素の `[` など）
- カナから母音ビセームへの写像
- 正規化感情からモーフ重みへの写像（VRM 恒等、PMX テーブル）
- 各コントローラ（まばたき、サッケード、呼吸、リップシンク）を `(時刻, 状態) -> 重みマップ` の純粋関数として検証する
- チャットの状態遷移（送信中、中断、エラー、再生成）

### 9.3 E2E

- WebdriverIO + tauri-driver を Windows 上で用い、スモークテストに限定する
- 対象: 起動、モデル未設定でのチャット送受信、モデル読み込み、3D ビューの表示切り替え

### 9.4 対象外

- three.js の描画結果そのもの（ビジュアルリグレッションは手動確認とする）
- 実際の LLM エンドポイントに対する自動テスト（手動の接続テスト機能で代替）

## 10. リスクと軽減策

| # | リスク | 影響 | 軽減策 |
|---|---|---|---|
| R-1 | three.js の `MMDLoader` は `examples/jsm` 配下にあり API 安定性の保証がない。PMX の物理演算に必要な ammo.js は大きな WASM 依存である | P1 の工数が読みにくい | `ModelAdapter` インターフェースで隔離する。P1 着手時に three.js のバージョン固定可否を判断する。物理演算は初期実装では任意機能とする |
| R-2 | 小規模ローカルモデルが感情タグ規約を無視する | 感情表現が機能しない | タグモードの切り替え（F-07-6）、few-shot 例のシステムプロンプトへの注入、`neutral` フォールバック（F-07-5） |
| R-3 | WebView2 の WebGL 性能は GPU ドライバに依存する。ソフトウェアフォールバックでは実用に耐えない | 描画が極端に遅い | 起動時にレンダラ情報を取得し、ソフトウェアレンダリング検出時に警告を表示する |
| R-4 | 大容量モデルによるメモリ消費 | クラッシュ | ファイルサイズの閾値で警告する。読み込み失敗を捕捉してアプリを継続させる |
| R-5 | shirataki は CeVIO AI 本体と Node サーバーの常駐が前提の外部依存である | P2 で連携が失敗する | 有効化前にヘルスチェックを行い、未起動時は明示的に案内する。TTS 無効でも本体機能が完全に動作すること |
| R-6 | PMX モデルのモーフ名が多様でマッピングが破綻する | PMX の表情が出ない | 既定推測テーブル＋UI での手動再割り当て（6.3 節）。マッピング未設定でも表情なしで表示は成立させる |
| R-7 | MMD モデルの利用規約違反 | 権利上の問題 | モデルを一切同梱しない。PMX 読み込み時に規約確認の注意表示を行う（4.4 節） |
| R-8 | プロバイダ API の仕様変更 | 接続不能 | アダプタ層に閉じ込め、フィクスチャベースのテストで差分を検知しやすくする |
| R-9 | 推論モデルは思考にトークンを使い切り、本文を返さないことがある | 返事が出ない | `max_tokens` を既定で送らない。本文が空なら理由を表示する（ADR-0013） |
| R-10 | 表情・テクスチャの読み込み失敗が何のエラーも出さずに起きる | 原因が分からない | 読み込み後にテクスチャ数と表情数を数え、0 なら警告する。診断パネルから素性を確認できる |
| R-11 | 画面側の例外がログに残らない | 「エラーになる」としか分からず調査できない | 捕まえられなかった例外と Promise の拒否を Rust のログへ送る。描画が落ちたときは白い窓ではなく理由を出す |
| R-12 | PMX はモーフ名・ボーン名に標準が無く、モデルごとの手当てが際限なく必要になる | 保守が続かない | 実験的対応と位置づけ、表示・テクスチャ・揺れ物までに範囲を限る (ADR-0015) |

## 12. 未決事項

設計フェーズ（2026-08-29）で以下のとおり解決した。残る未決は実装中に実測して定める項目のみである。

| # | 項目 | 状態 |
|---|---|---|
| U-1 | フロントエンドのフレームワーク | **解決。** React + TypeScript。3D キャンバスは React の管理外（[ADR-0007](adr/0007-react-with-canvas-outside.md)） |
| U-2 | 状態管理ライブラリ | **解決。** Zustand（[ADR-0008](adr/0008-zustand-for-state.md)） |
| U-3 | 会話履歴のストレージ | **解決。** JSON ファイル。SQLite への移行基準を明記（[ADR-0010](adr/0010-json-conversation-storage.md)） |
| U-4 | コンテキストウィンドウの既定ターン数 | **解決。** 直近 20 ターンを上限とし、併せて推定トークン量が `contextBudgetTokens` を超えないよう古い順に落とす。既定予算はモデル文脈長の 50%、不明な場合は 8,000 トークン。日本語は保守的に 1 文字 = 1 トークンで見積もる |
| U-5 | 疑似リップシンクの消化レート既定値 | **暫定決定。** 毎秒 10 文字を既定とし `Settings.lipSyncCharsPerSecond` で変更可能とする。最終値は実機で調整する |
| U-6 | 感情タグの語彙を拡張可能にするか | **解決。** MVP では 6 種に固定する。理由は `emotion-protocol.md` 1.1 |
| U-7 | アプリ名およびウィンドウタイトル | **解決。** `moca` とする |
| U-8 | ロギング方針 | **解決。** `tracing` + 日次ローテーション 7 日保持。機密は `Secret` newtype で保護（[ADR-0011](adr/0011-tracing-and-secret-masking.md)） |
| U-9 | 感情遷移の補間時間 | **未決。** 200〜300ms を初期値とし、実機の見た目で確定する |
| U-11 | 推論モデル向けの既定設定 | **未決。** 思考が長いモデルでは初回応答までの待ち時間が大きい。プロバイダ種別ごとに既定値を変える余地がある |
| U-10 | モデルファイルサイズの警告閾値 | **未決。** 実測してから定める。暫定 150MB |
