# ADR-0004: MVP は VRM のみ。PMX は ModelAdapter の背後に置く

- 状態: 採択
- 日付: 2026-08-29

## 文脈

要件として VRM と PMX の双方を扱う。しかし両者は表情表現の標準化の度合いが決定的に異なる。

VRM は表情プリセット（`happy` / `angry` / `sad` / `relaxed` / `surprised` / `neutral`）を仕様として定めており、どの VRM モデルでも同じ名前で同じ意味の表情が得られる。

PMX にはこれがない。モーフ名は日本語であり（「笑い」「にこり」「困る」「怒り」「びっくり」など）、制作者ごとに命名も構成も異なる。同じ「笑顔」を作るのに必要なモーフの組み合わせがモデルごとに違う。

## 決定

MVP (P0) では VRM のみを実装する。PMX は P1 とする。ただし `ModelAdapter` インターフェースは MVP の時点で定義し、VRM 実装をその背後に置く。

## 検討した代替案

**両形式を同時に実装する。** 採用しない。PMX はモデル別マッピングの保存機構と再割り当て UI が不可欠であり、さらに `MMDLoader` と ammo.js による物理演算が加わる。MVP の目的は感情表現の設計を検証することであり、そこへ到達する前に形式差の吸収で工数を消費する。

**抽象化せず VRM 直結で書き、PMX 対応時にリファクタする。** 採用しない。感情から表情への解決経路が VRM の恒等マッピング前提で書かれると、PMX 対応時に `ExpressionController` から `MorphApplier` までの広範囲が影響を受ける。インターフェース 1 枚を先に引く費用のほうが安い。

## 影響

- `ModelAdapter` は MVP 時点で `VrmAdapter` 1 実装のみを持つ。実装が 1 つしかない抽象は本来避けるべきだが、ここでは P1 の存在が確定しているため正当化される
- `resolveEmotion()` がモデル側に「この感情を表現できるか」を問う形になる。VRM 0.x に `surprised` が存在しない問題もこの経路で扱える
- UI 上、PMX は「未対応」と明示する。読み込もうとしたときに無言で失敗させない
- PMX 着手時に必要になるもの: モーフ名の推測テーブル、`EmotionMapping` の永続化、再割り当て UI、物理演算の有効・無効切り替え
