# ADR-0019: 身振りは利用者が与える VRMA で行う

- 状態: 採択
- 日付: 2026-09-05
- 関連: 要件 F-15、F-14、[ADR-0004](0004-vrm-first-pmx-behind-adapter.md)、[ADR-0014](0014-emotion-synced-to-speech.md)、[ADR-0015](0015-pmx-via-third-party-loader.md)、[ADR-0017](0017-vrm-pmx-only.md)

## 文脈

0.7 で感情に応じた姿勢と待機の動きを入れた（F-14）。いずれも関節を回して作る
手続きの動きである。そのとき **「モーションクリップは読まない」** と決めた。
理由は 2 つだった。

1. VRMA や VMD のデータは同梱できない
2. 利用者に用意させて割り当てさせるのでは、PMX のモーフ割り当てと同じ負担になる

しかし身振り（F-15）はその方針のままでは作れない。手を振る・お辞儀する・指す
といった動作は、腕の長さに依らず手先を目標へ届かせる必要がある。関節を順に
回すだけでは円弧を描く機械的な動きになり、手が胴へ入る。逆運動学を入れるか、
モーションクリップを読むかの二択になる。

## 決定

**「既定の動きをクリップで作らない」という決定は変えない。素の moca は VRM さえ
あれば何も用意せずに動く。** そのうえで、**利用者が任意で足せる口だけを開ける。**

VRMA を読み込んで好きなタグ名を付けると、その名前がシステムプロンプトへ載る。
返答にそのタグが出たら、割り当てたモーションを再生する。割り当てが一つも
無ければ、プロンプトは 0.7 までと一字も変わらない。

### PMX のモーフ割り当てとは性質が違う

2 の理由はこの決定の前提だったので、なぜ当てはまらないかを書いておく。

| | PMX のモーフ割り当て | VRMA の身振り割り当て |
|---|---|---|
| 割り当てないと | **感情表現がまったく動かない** | 何も起きないだけ |
| 感情の表情・姿勢・待機の動き | 死ぬ | 従来どおり動く |
| 位置づけ | 必須の手当て | 任意の上乗せ |

PMX では、割り当てを済ませるまで moca の中心的な価値（返答に応じて表情が変わる）
が働かない。だからあれは負担だった。身振りは、足さなければ 0.7 のままである。

### タグの顔ぶれは利用者が決める

`[wave]` `[nod]` のような名前を moca 側で固定しない。利用者が VRMA に名前を
付け、その名前がプロンプトへ書き足される。**キャラクターごとに違う持ち技を
持たせられる。**

固定しないのは、moca が動きの中身を知らないからである。`[wave]` という名前で
何が起きるかは読み込んだファイル次第で、moca には確かめる手立てが無い。名前を
決められるのは、ファイルを選んだ本人だけである。

割り当てはキャラクタープロファイルに持つ。人格ごとに違ってよく、感情の割り当て
（`emotionMapping`）や声の設定（`voiceSettings`）と同じ単位になる。

### 知らないタグは本文のまま返す

パーサは、割り当てられたタグ名だけを身振りとして解決する。**渡されていない
名前は従来どおり本文として表示する**（`emotion-protocol.md` 3.6 の劣化規則）。

すべての `[...]` を身振りとして飲み込むほうが簡単に見えるが、それをすると本文中
の `[検索]` のような角括弧まで消える。「本文を絶対に失わない」という設計原則
（3.6）のほうが重い。

タグ名は英小文字だけに限る。パーサの文法（`[a-z]+`）がそうなっており、外れた
名前を付けると本文として画面に出てしまう。感情タグと同じ名前も使えない。

### クリップは体の回転だけを使う

VRMA は表情も視線も腰の移動も持てるが、moca は**人型ボーンの回転しか使わない**。

**表情と視線を渡さないのは、読み上げ中のリップシンクと感情の表情を上書きして
しまうからである。** 手を振っているあいだ口が動かなくなる、というのは moca に
とって芯を損なう壊れ方になる。表情は返答に応じて変わり続けなければならない。

**腰の移動を使わないのは、マスコット表示が外接箱に合わせて窓を詰めているから
である**（F-13-4）。動いているあいだに位置が変わると、モデルが枠から出る。

### クリップはモデルの立ち姿へ載せ替える

**クリップの回転をそのままボーンへ書かない。先頭のコマからの差を取り、モデルの
立ち姿へ左から掛ける。**

```
世界(t) = 世界(親, t) × ローカル(t)
目標(t) = ( 世界(t) × 世界(0)⁻¹ ) × 立ち姿の世界での向き
出力(t) = 目標(親, t)⁻¹ × 目標(t)
```

置き換えでは、クリップが書いた角度がそのままボーンに載る。ところが **「腕を
下ろした姿勢」はモデルごとに違う。** moca の立ち姿の調整は「これより高い腕を
下ろす」下限を与えるだけで（`DEFAULT_ARM_DECLINATION_DEGREES`）、元から低い腕は
そのまま垂れる。クリップの休め姿勢と食い違えば、**その差のぶんだけ身振りの前後で
腕が跳ねる。**

実際に起きた。水平から 35 度下がった腕を休め姿勢として作ったクリップを、腕が
75 度垂れるモデルで再生したところ、始めと終わりに腕が外へ 40 度開いた。録画を
コマで追うと、開き切った角度は 35 度、すなわちクリップ側の休め姿勢そのもの
だった。

差を取れば、どの立ち姿から始めても同じ「動き」が乗る。**利用者が拾ってきた VRMA
にも効く。** どんな休め姿勢で作られていようと、moca は差だけを取る。

**世界で差を取るのが要点である。** 骨のローカル回転だけを見て差を取ると、二つの
壊れ方をする。どちらも実際に通った道なので書き留めておく。

**骨自身の側（右）から掛けると、差の回転軸が土台の姿勢ごと傾く。** three.js の
加算ブレンド（`makeClipAdditive` + `AdditiveAnimationBlendMode`）がこれにあたる。
替えてみたところ跳ねは消えたが、腕を持ち上げるはずの動きが外へ開く動きに変わった。
40 度傾いた軸で回っていたためである。

**親の側（左）から掛けると腕は直るが、今度は手の向きが崩れる。** 骨は繋がって
いるので、祖先の立ち姿の差がその先の骨の座標系ごと回してしまう。腕の付け根で
40 度違えば、手首の回転軸も 40 度回る。腕の動きは合っているのに手のひらが
あらぬ方を向く、という形で出た。

### 腕は相対、手は絶対

**腕と手では、保つべきものが違う。**

- **肩と肘は「手をどこへ運ぶか」を決める。** 腕の長さも立ち姿もモデルごとに
  違うので、相対で載せ替える
- **手首は「手が何を見せるか」を決める。** 手のひらをこちらへ向ける、というのは
  **絶対の向きに意味がある。** 相対で載せると、腕の付け根の立ち姿の差のぶんだけ
  手のひらが回る。腕の動きは正しいのに手だけがあらぬ方を向く

そこで手だけは、クリップの世界での向きをそのまま使う。**ただし丸ごと従うと、
モデルによっては手首が人の可動域を超える。** ひねりと曲げを分けて扱う。

- **ひねり**（前腕の軸まわり、回内・回外）は可動域が広い。±80 度以上動くので、
  クリップの向きに素直に従わせる。上限を設けない
- **曲げ**（軸に垂直、掌屈・背屈・橈屈・尺屈）は狭い。掌屈と背屈で 70 度ほど、
  橈屈・尺屈は 20〜30 度しかない。立ち姿からの差として 70 度で頭打ちにする

手首をひねって見せたい面を向けるのは、人が実際にしていることでもある。腕を
どこへ上げようと、手のひらは相手のほうへ向ける。

**向きを合わせるのは、手を上げているあいだだけにする。** 二つの条件で測る。

- **動き出してから合わせる。** 始めから絶対の向きにすると、腕がまだ立ち姿に
  いるうちに手首だけが先に回る。上げ始めに手がひとりでにねじれて見えた。
  0.35 秒かけて寄せる
- **前腕がどれだけ動いたかで決める。** 休め姿勢から 20 度動くまでは合わせず、
  50 度で合わせ切る。**腕を下ろすときに手のひらが前を向いたままになるのを防ぐ。**
  人は腕を下ろすとき手のひらを前へ向けたままにしない。肩が内へ回り、手のひらは
  腿のほうを向く

手のひらを相手へ向けるのは「見せている」あいだの振る舞いである。上げも下ろしも
していない腕には、向けるべき面が無い。

計算は `src/domain/motion/retarget.ts` にあり、試験で守っている。

代償として、**上げ切った先の絶対的な位置は保証されない。** 腕が低く垂れる
モデルでは、手の到達点もそのぶん低くなる。跳ねることに比べれば軽い。位置を
決め打ちしたいなら逆運動学が要るが、それは 0.8 で採らなかった道である。

強さ（`[wave:0.5]`）は差分の重みになる。置き換えのときは「基準の姿勢との中間」
という間接的な意味だったが、差分では動きの大きさそのものを表す。

### 終わりは立ち姿へ閉じる

**クリップの終わりが始まりと同じ姿勢とは限らない。** 撮影ものでは、手だけが違う
向きで終わっていることがある。載せ替えは始まりを基準に差を取るので、その差は
最後まで残る。放っておくと、身振りのあとに手首が回ったままになる。

実際に起きた。撮影の始まりが「手の甲が前」という向きだったため、終わりでは
90 度ほど回った差がモデルの立ち姿へ乗り、腕を下ろしたのに手のひらが前を向いて
いた。

最後の 0.3 秒で立ち姿へ閉じる。要件 F-15-3「身振りは一定時間で終わり、元の姿勢
へ戻ること」を、ここで守る。**利用者が用意したクリップの終い方に頼らない。**

### 手続きの姿勢とクリップの順序

同じボーンを、呼吸・待機・感情（F-14）とクリップの双方が動かしうる。**クリップ
を後に書く。** クリップが動かすボーンはクリップが持ち、触らないボーンには呼吸や
待機が残る。

足し合わせないのは、`applyPose` が基準の姿勢からの差を絶対値で書く仕組みだから
である（F-14）。クリップの回転へ差を足すには基準そのものを毎フレーム取り直す
必要があり、層が増えるほど破綻しやすくなる。身振りは 1〜3 秒で終わるので、その
あいだ待機の揺れが止まっても差し支えない。

一度に動かすのは 1 つだけとする。重ねると腕が二重に振れる。

### 読み上げに合わせて出す

身振りは、対応する本文が読まれる位置で始める。感情の切り替えと同じ扱いで、
音声があるならその音声の先頭に合わせる（[ADR-0014](0014-emotion-synced-to-speech.md)）。
解釈した時点で動かすと、合成を待っているあいだに手だけが先に動く。

## 帰結

- 身振りを使わない利用者にとって、moca は 0.7 と何も変わらない
- VRM のみが対象になる。VRMA は VRM の人型ボーンを前提とするので、PMX には
  当たらない（[ADR-0015](0015-pmx-via-third-party-loader.md)）
- **動きの品質は利用者が用意したファイルで決まる。** 手続きの動きと違い、moca
  には良し悪しを判断する手立てが無い。診断パネルで試せるようにして、目で確かめて
  もらう
- **試す場所は診断パネルに置く。設定画面には置かない。** 設定は全面を覆う
  ダイアログなので、そこで動かしても背後のモデルが見えない。診断は横に開く板で、
  モデルを見たまま押せる。表情の確認ボタンが診断にあるのと同じ理由である
- VRMA の中身は IPC を通らない。モデルと同じくアセットプロトコルで WebView が
  直接読む（`ipc-contract.md` 2.5）
- モーションクリップを読む足回りができたので、将来ここへ既定の動きを載せる道は
  残る。ただし同梱物を増やす判断は別途行う（ロードマップ「その先」）
