# ADR-0003: 感情表現にインラインタグ方式を用いる

- 状態: 採択
- 日付: 2026-08-29

## 文脈

LLM の応答からキャラクターの感情を取り出す必要がある（要件 F-07）。取り出し方には主に 3 つの方式がある。

1. 構造化出力 / tool calling で `{ "emotion": "happy", "text": "..." }` を得る
2. 応答本文にインラインでタグを埋め込む
3. 応答完了後に別途分類器を通す

同時に、応答はストリーミング表示する必要がある（要件 F-05-2）。また接続先には Ollama 上の 7B 〜 8B 級ローカルモデルが含まれる（要件 F-06-2）。

## 決定

応答本文にインラインで感情タグを埋め込む方式を採る。

```
[happy]こんにちは。[surprised]えっ、本当ですか。
```

文法とパーサ仕様は `docs/emotion-protocol.md` に定める。

## 検討した代替案

**構造化出力 / JSON。** 採用しない。決定的な理由は**ストリーミングと両立しないこと**である。JSON は文書が閉じるまで妥当な解釈ができないため、逐次表示するには不完全 JSON のパースという別の困難を招く。加えて、小規模ローカルモデルは厳密なスキーマ遵守に失敗しやすく、失敗時に本文ごと壊れる。1 応答に感情を 1 つしか付けられない設計になりやすい点も、体験上の損失が大きい。

**応答後の分類器。** 採用しない。追加の推論 1 往復ぶんの遅延が発生し、かつ発話中に感情が変化する表現ができない。

## 影響

- 発話の途中で感情が変化する表現が可能になる。これが「生きている感」の主因となる
- パーサは**チャンク境界をまたぐ部分タグ**を扱う必要がある。`[hap` と `py]` が別チャンクで到着する。ここが本プロジェクト最大のバグ源であり、単体テストの重点対象とする
- 本文中に素の `[` が現れた場合の誤検出対策が必要。`MAX_TAG_LEN` による打ち切りで対処する
- モデルが規約に従わない可能性を常に前提とする。未知タグ・タグ欠如・破損タグのいずれでも本文を失わないことを不変条件とする
- 感情推定を無効化する設定（`emotionMode: "off"`）を用意し、規約に従わないモデルでも本体機能が成立するようにする
